# Teardown: devices, parameter model and parameter controls

Feeds: O04 (device/effect instance), O05 (parameter) · A06 device chain/effects · A05 LAYER panel · A19 MIDI.
Refs read: Vital (GPL, patterns only), Surge XT (GPL, patterns only), Tweakpane (MIT), Cockos WDL (permissive). Ableton device chain is OBSERVE tier and was not observed in this pass.
Legal: GPL repos were read for behavior and structure. Everything below is described in my own words. No code, identifiers beyond file/symbol citations, or algorithms are reproduced.

## Problem in Creatrix today

1. **Parameter definition is a small interface.** `ParamDef` (`frontend/src/shared/types.ts:545-555`) has `type` (`float|int|bool|choice`), `min`, `max`, `default`, `label`, `description`, `options`, `curve` (`linear|logarithmic|exponential|s-curve`) and `unit`. It has no display scaling, no "step", no "bipolar" flag and no version stamp. Value formatting happens in `formatParamValue(value, type, unit, max)` (`Knob.tsx:218`) and not from the definition.
2. **Knob interactions are documented in a header comment and not in a spec** (`components/common/Knob.tsx:69-80`):
   - Vertical drag adjusts the value.
   - Shift+drag is 10x finer (`SENSITIVITY_FINE` 0.001 vs 0.005, `:41-43`).
   - Cmd/Ctrl+drag is 4x **coarser** (0.02).
   - Wheel steps are 0.004 / 0.02 / 0.08 (`:46-48`).
   - Double-click opens typed entry.
   - **Right-click resets to default** (`handleContextMenu`, `:149-152`).
   - Arrow keys step 1% (Shift 10%).
   - The knob is exposed as `role="slider"` with `aria-valuetext` (`:213-219`).
3. **A right-click collision exists.** `Knob.handleContextMenu` resets the value and does not stop propagation (the only `stopPropagation` calls in the file are at `:158` and `:162`, in the key handler). The parent `div.device-card__param` has its own `onContextMenu` that opens the param menu when `onParamContextMenu` is passed (`DeviceCard.tsx:418-430`, wired at `DeviceChain.tsx:566` when the track is not a pad target). So on a track chain a right-click on a knob can both reset the value and open the Automate menu. This needs a runtime check (not run here) before the spec states it as fact.
4. **Modifier convention differs from the neighbouring tools.** Cmd/Ctrl is *coarse* in Creatrix. In Vital the Cmd modifier selects the finer "sensitive" mode (see #3), and in WDL/REAPER-style sliders Ctrl is the fine modifier (#4).
5. **Param tile has many adornments with ad-hoc order.** `DeviceCard.tsx:431-470` renders: knob, CC badge (`:445`), automated dot (`:446-452`), field-assign `Select` (`:453-470`, only for field-capable params) and "field" badge/gain/invert/clear on a field-assigned param (`:363-392`). The order, the hover set and the visibility rules are not specified.
6. **The live modulation readout exists.** `ghostValue = modulatedValues?.[key] ?? value` is passed to `Knob` (`DeviceCard.tsx:403, 441`) and shows the modulated value on the knob. It is a single ghost handle with no "range of modulation" arc.
7. **Mapping creation by drop exists, and it always creates a new operator.** Dropping an operator *type* on a param (`handleParamDrop`, `DeviceCard.tsx:232-262`) calls `addOperator(type)` and then `addMapping(created.id, {targetEffectId: effect.id, targetParamKey: key, depth: 1.0, min: 0, max: 1, curve: 'linear'})`. An existing operator cannot be dragged to a second param. The default depth is a flat 1.0 regardless of the param's current position. An operator cap (`LIMITS.MAX_OPERATORS`) is surfaced by a rate-limited warning toast (`:242-247`).
8. **Chain-level facts.** `LIMITS.MAX_EFFECTS_PER_CHAIN = 10` (`shared/limits.ts:28`). The chain header shows `n / 10` (`DeviceChain.tsx:~513-518`). Each device has enable toggle (`data-testid="device-toggle"`, `DeviceCard.tsx:326`), name, remove, A/B switch (`ABSwitch.tsx`), mix slider (`:505-520`), matte chip and mask row (`:530-580`).
9. **Param identity depends on the owner.** Automation uses `paramPath = ${effect.id}.${key}` (`DeviceCard.tsx:147`). CC mappings match `effectId === effect.id` (`:404-406`). Operator mappings use `targetEffectId`. Instrument macros use `pad.<padId>.<param>` (`components/instruments/types.ts:371-378`). See automation-modulation.md for the identity problem.

## Recommendation for the spec

1. **(#1, #2)** Define the parameter record once (O05): key, label, type, range, default, response curve, unit, display transform, step, bipolar, version stamp. Every writer (knob, typed entry, automation, MIDI CC, operator, macro, project load) clamps through it. Add a "who writes a param" table.
2. **(#3, #4, Problem 2, Problem 4)** Write ONE interaction table for the parameter control: drag, fine, coarse, wheel, double-click, right-click, Alt-click, keyboard. Present the cross-tool evidence (Creatrix vs Vital vs WDL vs Tweakpane keyboard) and ask the owner to pick. Do not change the current behavior in the spec without that decision.
3. **(Problem 3)** The spec states the right-click contract explicitly (reset or menu, not both). Add a Playwright-free component test against the testids `param-knob-{effectId}-{key}` once decided.
4. **(#6)** Specify a drag readout: contents (name, formatted value, modulation delta), placement, and the 12px floor (D6).
5. **(#7)** Specify typed-entry validation: accepted formats, units, out-of-range handling (clamp vs reject), error text and focus return.
6. **(#8)** State the authored/effective split: the knob arc shows authored, the ghost shows effective. Only authored is saved.
7. **(Problem 5)** List the adornments in a fixed order with visibility rules: CC badge, automated dot, modulation indicator, field badge. One row per adornment in the component spec.
8. **(#10)** The per-param context menu contains the param's lanes and mappings with remove and mute. Link to the automation-modulation spec.
9. **(#11)** Treat instrument macros and operators as two producers of the same "modulation source" concept in the O07 spec, even if the UI stays separate.
10. **(Problem 7, #10)** Specify the drag-to-assign contract for an *existing* operator, not just a new one (see automation-modulation.md recs 4-5).
11. **(#9)** If the registry gets param groups, folders are the display mechanism. Otherwise skip.

## Library evidence

- **Tweakpane** (MIT, v4.0.5). It is vanilla TypeScript with a plugin model; there is no React binding in the clone (`packages/tweakpane/src/main/ts/`). It provides constraints (#2), two-way bindings (#8) and folders (#9). It does not provide rotary knobs, automation indicators or modulation arcs. Adopting it as a *parameter-panel renderer* would mean a wrapper per panel, a restyle to the token system and a loss of the Knob's ARIA slider contract unless re-added. Bundle size was not measured. As a source of **ideas** (constraints, refresh semantics) it needs no dependency.
- **Vital / Surge**: GPL, no adoption path. Patterns only.
- **WDL**: C++ toolkit, no adoption path in a React/Electron renderer.

## Candidate additions (owner approval required)

1. **Param groups / folders** in device cards driven by the effect registry (#9).
2. **Drag readout bubble** with modulation delta (#6), if D6 sizing allows.
3. **Param menu that lists and manages its modulation routings** (#10), beyond the current Automate-only menu. (The menu itself exists, so this extends it.)
4. **A shared "ParamAddress" value type** is a spec matter and not a feature: see automation-modulation.md. It is not listed as an addition.
