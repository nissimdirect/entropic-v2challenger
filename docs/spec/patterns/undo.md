# Pattern teardown: undo / history

Phase-2 reader output. Legal tiers per `PLAN.md`: Olive, Kdenlive, Ardour = READ (GPL, patterns only, own words); OpenTimelineIO and React Aria = ADOPT but neither ships an undo system (OTIO is a data model only; React Aria has no history), so they contribute no rows here. Refs cloned to `~/Development/_refs/` (read-only).

## Problem in Creatrix today

1. **Drag gestures create one undo entry per pointer-move.** `Clip.tsx` clip-move calls `moveClip` from every `pointermove` (`components/timeline/Clip.tsx:524`), and trim-left/right call `trimClipIn`/`trimClipOut` per move (`Clip.tsx:627`, `:653`). Each of those store actions wraps its change in `undoable(...)` (`stores/timeline.ts:1441` "Move clip", `:1494` "Trim clip in", `:1533` "Trim clip out"). There is no `beginTransaction`/`commitTransaction` around them (the only gesture transactions are slip/slide, `Clip.tsx:354-418`, plus the audio batch delete, `stores/timeline.ts:2667`). Net effect: one drag fills the 500-entry stack (`stores/undo.ts:12`) with dozens of intermediate positions, and Cmd+Z walks back through pixels instead of one gesture. Slip/slide prove the transaction pattern already works; move/trim were never ported.
2. **Freeze / unfreeze create no undo entry** (known gap). `handleFreeze` / `handleUnfreeze` (`App.tsx:2410-2452`) call `useFreezeStore.freezePrefix/unfreezePrefix` directly; those store actions (`stores/freeze.ts:49`, `:76`) mutate `frozenPrefixes` and talk to the sidecar (`freeze_prefix`, `invalidate_cache`) with no `undoable`. Freeze is also async and has a backend side-effect (cache id), so the existing sync `undoable(description, forward, inverse)` contract (`stores/undo.ts:206`) does not fit it as-is.
3. **Undo while a transaction is open is unguarded.** `undo()` (`stores/undo.ts:85`) pops `past` without checking `_transaction`; mid-drag Cmd+Z would invert an older entry while the buffered entries are live. `beginTransaction` while one is open silently commits the previous one (`stores/undo.ts:127-132`), so a missed `pointerup` (blur, Esc) commits a half-gesture instead of aborting.
4. **`undo()`/`redo()` do not catch a throwing inverse/forward** (`stores/undo.ts:85-120`); only `execute`/`undoable` do (`:63`, `:206`). A throwing inverse leaves the stack unchanged but state half-applied.
5. **No Esc-abort on drags.** `abortTransaction` exists (`stores/undo.ts:188`) and slip/slide use it (`Clip.tsx:376`, `:418`), but move/trim have no abort path (no transaction), and the `Escape` hit at `Clip.tsx:197` is the rename input, not a drag.
6. **No history listing surface in the store contract.** `UndoEntry` is `{forward, inverse, description, timestamp}` (`shared/types.ts:559-564`); `past`/`future` are public arrays so a history panel (see `docs/mockups/history-panel.html`) can already read descriptions. No grouping/label conventions are specified beyond the `UNDO CONVENTIONS` header comment (`stores/undo.ts:1-6`).

## Recommendation for the spec

1. **Gesture contract (U4, U8, U1).** Every continuous pointer gesture (clip move, trim in/out, marker move, loop-handle drag, track reorder, knob/lane drags) follows one lifecycle: `start` -> live motion -> `commit` (exactly one undo entry, label verb-first) or `abort` (Esc / pointer-cancel / window blur restores the pre-gesture state, nothing pushed). Spec the choice once: either keep calling the store per move inside `beginTransaction`/`commitTransaction` (current slip/slide shape), or render the live position from local gesture state and call the store once at release. Either way move/trim must stop producing per-pixel entries (Problem 1).
2. **Esc aborts an in-flight gesture (U4)** and `pointercancel`/blur routes to abort, not commit (Problem 3, 5).
3. **Guard undo during a transaction (Problem 3).** While `_transaction != null`, Cmd+Z is ignored or first aborts the open gesture (spec picks one; abort matches Ardour U4 `aborted`). `beginTransaction` on an already-open transaction should be a programming error surfaced in dev, not a silent commit.
4. **Empty gestures leave no entry (U1)** - already true; keep as a stated invariant so a click on a clip without movement never dirties the project.
5. **Freeze / unfreeze are undoable (Problem 2).** Spec must resolve the async problem explicitly. Option A: undo entry whose forward/inverse call `freezePrefix`/`unfreezePrefix` (re-render cost on redo; entry carries `trackId`, `cutIndex`, prefix snapshot). Option B: treat the frozen prefix as a derived cache keyed on the chain (invalidated automatically when the chain changes) and make only the "cut marker" undoable (cheap, sync). Owner picks A or B; either way the user-visible rule is "Cmd+Z after Freeze removes the freeze".
6. **Throwing inverse/forward during undo/redo is handled like `execute` (Problem 4):** catch, toast with source `undo`, keep stack consistent.
7. **History labels (U3).** `description` is mandatory, verb-first, no ids, and is what the history panel shows; batch labels carry counts ("Remove 3 audio clips", `timeline.ts:2667`).

## Library evidence

None. Neither OTIO nor React Aria offers undo. Zustand store + `undoable()` is retained; Olive/Ardour/Kdenlive were read only for lifecycle patterns.
