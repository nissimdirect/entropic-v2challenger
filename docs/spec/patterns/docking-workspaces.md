# Teardown: docking, workspaces, floating panels, pop-out windows

Feeds: systems/docking · O17 · A01 shell/layout · A12 preview/monitors/multiwindow · **evidence for deferred verdict (c): adopt dockview or not.**
Refs read: dockview `mathuo/dockview` @ v8.8.3, MIT (`~/Development/_refs/dockview`). Reader stance: neutral. Evidence for and against is listed side by side and no adoption call is made.
Legal: dockview is ADOPT tier and was read freely. No GPL source was needed for this topic. Blender and Kdenlive are listed in PLAN.md for this topic but were not in this reader's brief, so they are not covered here.

## Problem in Creatrix today

1. **No docking model. The shell is a fixed CSS grid plus a handful of store scalars.** `frontend/src/renderer/styles/global.css:26-27` defines `grid-template-columns: var(--sidebar-width) 1fr; grid-template-rows: 1fr auto auto var(--statusbar-height)`. A panel's position is a code decision, not data.
2. **Layout state is two unrelated scalar bags in two localStorage keys.**
   - `STORAGE_KEY='entropic-layout'` (`stores/layout.ts:79`) holds sidebarCollapsed, timelineCollapsed, timelineHeight, deviceChainHeight and snapEnabled.
   - `CREATRIX_STORAGE_KEY='creatrix-layout'` (`stores/layout.ts:80`) holds leftColW, inspectorH, previewHPct and deviceChainH.
   - There are two device-chain heights (`deviceChainHeight` vs `deviceChainH`) with different clamp ranges (`stores/layout.ts:98` and the clamp calls in `setDeviceChainHeight`). That is one panel with two sources of truth.
3. **Persistence is hand-validated per field.** `loadPersistedLayout` and `loadPersistedCreatrixLayout` type-check and range-check each field, then fall back to `{}` on any exception. This is safe. It cannot express a tree, so it cannot express "which panel lives where".
4. **No named layouts or workspaces.** Nothing saves or restores an arrangement, and there is no reset-to-default beyond clearing storage. `toggleFocusMode` (`stores/layout.ts:214`) is the only layout "preset" and it flips two booleans.
5. **Ephemeral state is mixed in with persisted state.** `expandedTrackIds` (`:182`), `previewCollapsed` (`:188`) and `isPopOutOpen` (`:175`) are session-only. A workspace spec has to say which of these is workspace state and which is session state.
6. **One hard-coded pop-out, with its own transport.** The main process opens a second `BrowserWindow` (`frontend/src/main/pop-out-window.ts:132`). It has its own renderer entry (`renderer/pop-out-entry.tsx`, which mounts `PopOutPreview` only). Frames are relayed over IPC (`App.tsx:1765`, `window.entropic.sendFrameToPopOut(dataUrl)`). Its bounds persist to `~/.creatrix/pop-out-state.json` (`pop-out-window.ts:7`). It is a separate JS context. Only the preview can be popped out, and nothing else can.
7. **No floating panels.** There is no overlay-panel concept apart from dialogs and menus.
8. **Resize is per-edge custom handles** (the "Resize device chain panel" handle, `DeviceChain.tsx:476`) with ad-hoc clamps. There is no shared min/max constraint model.
9. **No panel drag-to-dock, tab stacking or keyboard docking.** Drag-and-drop in the app is HTML5 DnD for effects (`DeviceChain.tsx:183`, `dropEffect = 'copy'`), which is a different concern from panel DnD.

### Contrast with what Creatrix already has

- The existing pop-out already persists bounds, relays frames and handles the disconnect heartbeat (`pop-out-window.ts:18` heartbeat comment, `safeSend` at `:26-57`). These solve problems dockview does not address: frame transport and a render pipeline living in a separate process.
- Creatrix pop-out is a **monitor** (read-only, high-rate image stream). dockview pop-out is a **panel host** (interactive React tree). These are different jobs, and the spec should not conflate them.

## Recommendation for the spec

1. **(from #1, #2)** Define the layout as ONE versioned document (schema version, anchors, panel placements). It replaces `entropic-layout` and `creatrix-layout`, with a migration from both. Loading validates and falls back to the default layout without throwing to the user. This holds whether or not dockview is adopted.
2. **(from #3)** Every dockable panel gets a stable string id and a registered component key. An unknown id restores as a labelled placeholder (see states-empty-loading-error.md #5), not a crash.
3. **(from #4, D3, D10)** Declare which regions are **pinned** (D10 rail, D3 right LAYER panel, transport, status bar) and which are **free** (candidates: scopes, history, system monitor, mockup panels). Pinned regions are never user-rearrangeable. Only free regions use tab-stacking and docking, if the owner wants that at all.
4. **(from #11)** One declarative min/max size per panel replaces the five-plus clamp constants. The spec lists them in a table.
5. **(from #5, #12)** Spec collapse and maximize as two distinct operations on a panel (collapse-to-strip vs focus-maximize), with Cmd+B and F mapped explicitly.
6. **(from #7, #8, #9, #16)** Separate "monitor window" (the current preview pop-out: separate process, frame relay) from "panel window" (interactive, shared heap) in the spec. Decide each independently. State the failure and restore behaviors of any window: blocked, closed, display disconnected, bounds off-screen after a monitor change.
7. **(from #10)** If panel DnD is added, state its relationship to the existing HTML5 effect DnD. They share one drop-indicator vocabulary so there is not a second visual language.
8. **(from #13)** Any docking operation has a keyboard path and a live-region announcement string table. This is a requirement regardless of library.
9. **(from #14)** Dockview theming, if used, is a thin class that only aliases Tier-2 tokens. No literal hex (the existing `hex-ratchet.sh` rule).
10. **Session vs workspace state split** (Problem 5): the spec lists every layout-related field and tags it `workspace` (saved with layouts), `app` (survives sessions, not per layout) or `session` (never saved).

## Library evidence

dockview v8.8.3 (`packages/dockview-core/package.json`), license MIT, last commit in the clone Fri 2026-10-30.

| Axis | For adopting | Against / unknown |
|---|---|---|
| API fit | `toJSON`/`fromJSON`, groups, floats, edge groups, constraints, maximize and a typed event surface already cover items 1-5 and 11-12. React wrapper `dockview-react` (peer: React 16.8 to 19, so React 19 is covered; `packages/dockview-react/package.json:90-93`). | Group/tab stacking is the core model. It is only partially compatible with D3 and D10, which pin the rail and the right panel (pattern #4). The adoption cost is the work of constraining it, e.g. locking groups. A `locked` doc exists (`docs/core/locked.mdx`) but was not read in depth. |
| Pop-out | Built-in, multi-window, nested layouts, restoration lifecycle, failure results (#7, #9, #16). | Needs a same-origin, non-`file:` URL (#8). Production Creatrix is `file://` (`main/index.ts:247`). Moving DOM into a `window.open` child requires `nativeWindowOpen`-style behavior in Electron that was **not tested** here, and the clone must not be executed. Open question for a spike. Replacing the process-isolated monitor with a shared-heap window is also a design change. |
| Bundle size | `dockview-core` declares no runtime `dependencies` (`packages/dockview-core/package.json`), and `dockview-react` depends only on `dockview ^8.8.3` (`:87-89`). | **Gzip size was not measured** (no build was run per the brief). The README links a bundlephobia badge (`README.md:17`). Measure at the decision phase. |
| Accessibility | Keyboard docking, live-region announcements, overridable message table (#13). Rare among docking libraries. | Not verified in a running app. The tab and sash ARIA roles were not audited. |
| License | MIT, ADOPT tier. | None. |
| Maintenance | Active (recent commit, large API surface, CLAUDE.md/AGENTS.md in repo, e2e and jest tests present). | Large surface (core is 3,800+ lines in `dockviewComponent.ts` alone) means upgrade churn is possible. A major-version history was not reviewed. |
| Theming/density | CSS-variable theme plus SCSS mixins (#14). | Default chrome (tab height, gap) would need to be restyled to JetBrains Mono 12px floor (D5, D6). Effort not estimated. |
| DnD | Supports HTML5, pointer, or both, with a capability probe (#10). | Coexistence with the app's HTML5 effect DnD (`DeviceChain.tsx`) is untested. Drop-compass overlays (`dnd/dndCompass.mdx`) are extra visual vocabulary. |
| State fit | Layout JSON is plain data that can sit next to a Zustand store. | Panel React trees mount and unmount per dockview's `renderer` option. Creatrix stores are global singletons, so remounts should be safe, but the preview canvas and its frame loop are stateful (not checked). |

Net, stated neutrally: the layout-document and constraint ideas (#1, #2, #3, #11) are reusable with or without the library. The library's distinctive value (free docking and multi-window panels) matters only if the owner wants panels beyond the D3/D10 anchors. The pop-out transport is the main technical risk, and it is cheap to spike.

## Candidate additions (owner approval required)

These are new surfaces, not existing or planned scope.

1. **Named workspaces** (save/restore/rename/delete of a layout document, with a built-in default and a "Reset layout" action). Source: dockview `toJSON`/`fromJSON` (#1).
2. **Floating inspector or scope panels** over the preview (#6).
3. **Interactive panel pop-out** (e.g. device chain on a second monitor), distinct from the current preview monitor (#7).
4. **Maximize-one-panel** as a second focus mode alongside F (#12).
